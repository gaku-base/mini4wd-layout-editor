# ChatGPT・Codex レベル2開発フロー

## 目的

GitHub Issueを正式な作業指示、Pull Requestを実装結果として扱い、仕様整理・実装・自動検証・レビューの受け渡しを標準化する。

この運用は半自動とする。Codexは実装と検証を担当するが、`main`へのマージ、正式な寸法値の決定、仕様変更の最終承認は人が行う。

## 役割分担

### がくさん

- 目的、使い勝手、優先順位を決定する。
- 未確定寸法や操作仕様について最終判断する。
- Pull Requestの最終確認後にマージを承認する。

### ChatGPT

- 要望を実装可能なGitHub Issueへ整理する。
- 既存仕様、ロードマップ、Issue、Pull Requestの整合を確認する。
- Codexの実装結果、差分、自動テスト結果、未解決事項をレビューする。
- 仕様不足や判断が必要な点を、推測せず明示する。

### Codex

- 承認済みIssueの範囲内だけを実装する。
- Issueごとの作業ブランチを使用する。
- 型チェック、Lint、単体テスト、ビルドを実行する。
- 実装結果をPull Requestとして提出する。
- 不明な寸法や仕様を推測せず、作業を止めて未解決事項として報告する。

### GitHub Actions

Pull Requestと`main`へのpush時に以下を自動実行する。

```sh
npm run typecheck
npm run lint
npm test
npm run build
```

## 仕様の優先順位

矛盾がある場合は、次の順に扱う。

1. `AGENTS.md`の絶対条件
2. 承認済みの正式仕様書・decision log
3. 対象GitHub Issueの実装条件
4. ロードマップ
5. READMEや補助資料

Issueが上位仕様と矛盾する場合、Codexは勝手に解釈せず作業を停止する。

## 標準フロー

### 1. Issue作成

ChatGPTが`.github/ISSUE_TEMPLATE/codex-task.md`を基準にIssueを作成する。

Issueには最低限、以下を記載する。

- 目的
- 根拠となる仕様
- 実装範囲
- 対象外
- 変更禁止事項
- 完成条件
- 必須テスト
- 未決事項

### 2. 仕様承認

Codexを起動する前に、Issue内の次の条件を満たす。

- 実装範囲が一つの目的に絞られている。
- 未確認寸法を確定値として要求していない。
- 完成条件をテストで確認できる。
- 対象外と変更禁止事項が明記されている。
- がくさんの判断が必要な項目が分離されている。

### 3. Codex実行

承認済みIssueのコメントからCodexへ実装を依頼する。

実行指示には、次を含める。

- `AGENTS.md`を最優先で守ること。
- Issue本文の範囲だけを変更すること。
- `main`へ直接pushしないこと。
- 作業ブランチを作り、Draft Pull Requestを提出すること。
- 4種類の品質チェックを実行すること。
- 不明点を推測せず、PRの未解決事項へ記載すること。

ブランチ名の推奨形式：

```text
codex/issue-<番号>-<短い内容>
```

### 4. Pull Request提出

Pull Requestは`.github/pull_request_template.md`に従う。

Draft状態で提出し、最低限以下を記載する。

- 対応Issue
- 実装内容
- 変更ファイル
- テスト結果
- 使用した`verified` / `provisional` / `unknown`値
- 未解決事項
- 仕様書更新の有無
- 次の推奨タスク

### 5. 自動検証

GitHub Actionsが全項目成功するまで、レビュー完了とは扱わない。

失敗した場合は、ログを確認して同じ作業ブランチで修正する。テストを削除、無効化、緩和して通すことは禁止する。

### 6. ChatGPTレビュー

ChatGPTは次を確認する。

- Issueの完成条件を満たしているか。
- 指定外ファイルや機能を変更していないか。
- 未確認寸法をマジックナンバー化していないか。
- `indeterminate`や`unknown`を安全側に扱っているか。
- 自動テストが変更内容を実質的に検証しているか。
- UI変更がある場合、画面確認結果が添付されているか。
- 既存仕様変更時にdecision logが更新されているか。

### 7. 人による最終承認・マージ

以下を満たした後、がくさんがマージを承認する。

- GitHub Actions成功
- レビュー指摘解消
- 未解決事項が許容可能
- 必要な画面・操作確認完了

自動マージは使用しない。

## Codexが作業を停止すべき条件

- 未確認寸法を確定しなければ実装できない。
- `AGENTS.md`とIssueが矛盾する。
- Issue外の大規模リファクタリングが必要になる。
- 著作物、3Dモデル、画像、コードのコピーが必要になる。
- テスト失敗の原因が仕様判断を必要とする。
- 正常接続と干渉の区別を安全に判定できない。
- `clear`と断定する根拠が不足している。

この場合、推測で続行せず、実施済み内容と必要な判断をIssueまたはPull Requestに記載する。

## 並行作業ルール

完成期間を短縮するため、互いに独立した作業だけを並行化する。

並行化しやすい例：

- ドメインロジックとドキュメント整備
- UI試作と既存計算ロジックのテスト追加
- 保存形式設計と出力仕様整理

並行化しない例：

- 同じ型定義を変更する複数Issue
- 同じ衝突判定APIを同時に変更する作業
- 未確定寸法に依存する実装

原則として、同時進行は最大2件までとする。
